# 项目复盘

> 这份文档记录本项目从头到尾的**关键决策、踩过的坑和教训**，供以后维护或做类似项目时参考。
> 面向初学者，尽量用大白话。

---

## 一、项目起点与目标

**问题**：咪咕音乐网页版不向 Windows 报告播放信息（不写 `navigator.mediaSession`），导致：

- 按音量键的小卡片（SMTC）是空的；
- Lyricify Fusion 读不到当前歌曲，拿不到歌词。

**方案**：写一个脚本猫用户脚本充当"翻译官"，把网页上已经展示的歌名/歌手/封面/播放状态报给 Windows。

**最终形态**：单文件 `migu-smtc.user.js`，零依赖、零构建，改完即可用。

## 三、关键技术决策与取舍

### 1. 数据从哪来：只抄"屏幕上已经显示的"

- **决定**：只读取网页 DOM 中展示给用户的信息。
- **为什么**：合规红线（不破解、不下载、不上传），也最稳——咪咕再怎么改，界面上总得显示歌名。
- **代价**：一旦咪咕改版就得改选择器 → 用**可视化配置面板**把这个代价转嫁给用户自助解决。

### 2. 播放状态怎么判断：咪咕没有 `<audio>` 元素

- **发现**：侦察发现整个页面找不到 `<audio>`（用了非标准的播放实现方式）。
- **决定**：读取播放按钮的 `title` 属性反推状态——显示"暂停"代表正在播，显示"播放"代表已暂停。
- **教训**：不要假设所有网站都遵循标准做法，**先侦察再写代码**。

### 3. 同步调度：定时器不可靠，改用"时间戳限流"

- **发现**：窗口不可见时，Chromium 会把 `setTimeout` / `setInterval` 强制降速（500 毫秒可能变成几分钟）。
- **决定**：`MutationObserver` 回调里直接同步，用时间戳做限流；哨兵从"只盯播放条"改为"盯整页"。
- **教训**：**浏览器里凡是依赖"定时"的东西，在后台标签页/最小化窗口下都可能失灵**。

### 4. 咪咕内部数据源：多条路都走通过（或未通过）的经验

网站不更新界面时，我们先后尝试了 4 条"绕过界面"的路：

| 尝试 | 结果 | 结论 |
|---|---|---|
| 拦截网络请求 | 切歌时**根本没有新请求**（歌单早已整批下载） | 先看有没有请求再决定要不要拦 |
| 挖 Vue 的状态账本（Vuex / Pinia / 组件树） | 公共账本未暴露 | 框架不等于能拿到状态 |
| 拦截 `console.log`（咪咕每秒打印的心跳里有歌名和完整档案） | **失败**：它的日志模块在我们注入前就抢先保存了 `console.log` 引用，且即便改用更早的注入方式也晚到约 2 秒 | 先验证"注入时机"，别急着写解析逻辑 |
| 把封面下载下来转成内置图片（data URL） | 转换成功（靠 `GM_xmlhttpRequest` 绕过了跨域限制），但**窗口最小化时咪咕自己也不更新封面**，拿到的仍是旧图 | 下载不是瓶颈，**数据源**才是 |

### 5. 封面同步问题：根因不是我们

- **现象**：最小化时切歌，卡片封面停在上一首；恢复窗口的瞬间立刻更新。
- **根因**：Windows 版 Chromium 对不可见窗口**冻结渲染与定时器**，咪咕自己的封面也不更新（它的封面更新依赖渲染时机），我们读到的就是旧图。
- **取舍**：不再继续深入逆向咪咕内部（投入产出比低、易碎），而是：
  1. 在 README 明确写出**已知限制**与**两种缓解办法**；
  2. 保留已有效的机制（封面内置图片、可见时即时同步）。

## 四、可复用的经验：踩过的坑清单

1. **先侦察，后编码**：每到一个陌生网站，先用探针把元素/数据看清楚，一天的红气交换机位都比瞎猜强。
2. **先验证前提，再实现方案**："拦截 console" 前应先确认自己是否被更早注入，否则写了几百行也白搭。
3. **浏览器会对你撒谎**：定时器降速、惰性图片加载、渲染冻结——前台一切正常的表现，后台未必成立。
4. **连 Package 都不需要**：这类小工具脚本，零依赖 + 单文件的性价比最高。
5. **把"用户自助修复"做成功能**：配置面板 + 一键诊断，把一个难以避免的失效点变成可控的日常操作。
6. **一次一小步**：每次改动后都要实际在浏览器里跑一遍"应该看到什么"。
